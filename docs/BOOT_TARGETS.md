# Spit Fire / Jasper / GRUB 2 / Gates boot targets

The ISO's firmware-facing loader remains GRUB 2 (El Torito BIOS plus the GRUB EFI image for UEFI). Its top-level GRUB configuration opens the Spit Fire menu, which routes into the Jasper target manager. The separately assembled Spit Fire SF0 MBR and SF1/SF2 BIOS bootstrap artifacts are built and included under `/boot/spitfire/`; they are experimental raw-disk bootstrap outputs, not written over the ISO's El Torito boot sectors and not yet the ISO's active firmware loader. Jasper/GRUB 2 performs the actual ISO kernel and initramfs loading.

## Menu entries

- **Live — Aurora Desktop** — Debian Linux kernel, live initramfs, verbose diagnostics, then the Aurora startup splash and desktop.
- **Live — Safe Graphics** — Linux live environment with conservative 1024x768/800x600/640x480 graphics fallbacks and `nomodeset`.
- **Recovery — Linux Rescue Shell** — independent Linux runtime and read-only-first rescue interface. This remains the usable recovery option while native Koronos Recovery is blocked.
- **Installer — Native Koronos Installer** — dedicated native entry, fail-closed unless its own initramfs, separate installation payload, contract/phase/profile manifests, Koronos kernel, and an acceptance-generated `native-installer-runtime.ready` sentinel are all present.
- **Recovery — Native Koronos Recovery** — dedicated native entry, fail-closed unless its own recovery initramfs, manifest, Koronos kernel, and acceptance-generated `native-recovery-runtime.ready` sentinel are all present.
- **Koronos — Native kernel diagnostics** — experimental Multiboot2 kernel entry; its early entry/idle-loop marker is not a userspace-readiness claim.
- **Classic X / Openbox**, **boot diagnostics**, **UEFI firmware setup**, **GRUB command line**, **reboot**, and **power off**.

## Native runtime boundary

The ISO builder creates separate Installer and Recovery candidate images and embeds their manifests and SHA-256 records under `/boot/candidates/`. The current Installer image is a BusyBox diagnostic/runtime shell plus OS-specific metadata; the Recovery image is a dedicated recovery initramfs. These are build candidates, not certified native Koronos userspace. Neither READY sentinel is generated by the ISO build. The menu will not hand off to either native target until the required artifact set and a separate acceptance process produce the sentinel. Do not rename Linux Rescue as native Koronos Recovery.

## Graphics, diagnostics and artwork

GRUB prefers 5120x2880, then supported 4K/QHD/Full-HD modes, and falls back through 1024x768, 800x600 and 640x480. `gfxpayload=keep` asks GRUB to preserve its framebuffer; firmware and hardware may expose lower modes. The embedded wallpaper set supplies the default background for the Spit Fire and Jasper menus and the default Aurora desktop background.

Boot output is deliberately verbose: `loglevel=7`, `ignore_loglevel`, `earlycon=uart,io,0x3f8,115200`, `log_buf_len=4M`, timestamped printk, systemd status/debug output, and udev debug output. The serial console is 115200 baud.

## Init.mp4 startup

After a Linux-backed menu selection boots and Openbox is ready, Aurora plays `/usr/share/chimera/aurora/assets/Init.mp4` before starting the desktop or dispatching the selected Linux Live/Rescue mode. If the tracked source video is missing or empty, the ISO build synthesizes a short 1920x1080 MP4 from the embedded wallpaper frames and validates the resulting video stream. GRUB itself does not decode MP4, and the native Koronos kernel/Installer/Recovery candidates do not yet provide a media playback runtime; no video playback is claimed for those native handoffs.

## Verification

The live ISO workflow validates the BIOS/UEFI El Torito layout, embedded Koronos ELF64/Multiboot2 header, both GRUB menu layers, candidate image presence and manifests, Init.mp4, and the application bundle. QEMU exercises the Live target, native Installer/Recovery refusal paths, the separate Linux Rescue shell, and Koronos early entry markers. Physical-machine BIOS/UEFI boot and production Koronos userspace acceptance remain separate gates.
