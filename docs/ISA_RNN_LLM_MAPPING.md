# ISA mapping, learning corpus, and installer hardware advice

## ISA inventory and properties

The canonical `isa/isa_database.json` retains architecture rows (ID, class, family, nominal word width, status, encoding model, source reference, and verified-form count), instruction forms, source registry, and execution-model metadata. Consumers should preserve all fields and any future properties instead of projecting only mnemonic and opcode. Store source-spec revision, vendor/model applicability, profile, extension dependencies, privilege level, side effects, exceptions, memory-ordering behavior, feature requirements, and validation status when authoritative references provide them. Unknown values must remain unknown rather than being generated by a model.

## Mapping and learning

`tools/isa/chimera_isa_mapper.py` is a deterministic retrieval baseline and corpus collector, not a trained RNN/LLM. It preserves positive and negative candidates, source provenance, database version, target properties, and validation status in JSONL observations. Optional model scores affect ranking only; they cannot create encodings or authorize execution. Keep human-reviewed/conformance-tested labels separate from model-generated hypotheses. Split datasets by ISA family and specification version to reduce leakage. Do not include user source code or prompts in a training corpus without explicit consent.

## Installer hardware advice

`tools/installer/chimera_hardware_advisor.py` provides a conservative, explainable baseline for installer recommendations. It accepts detected or user-provided JSON facts for CPU architecture/model/features, RAM, storage/free space, firmware, Secure Boot, TPM, GPU, network, battery and intended use case. Unknown facts are surfaced as questions/checks, not guessed. It recommends edition/profile and optional package tiers, but does not install drivers, change firmware, repartition disks, or assert that an ISA catalog entry means the kernel supports the machine.

Example:
```sh
python3 tools/installer/chimera_hardware_advisor.py --facts hardware-facts.json
```

The installer UI should show each recommendation with the detected fact and reason, allow the user to correct facts, provide a safe fallback path, and ask explicit confirmation before any destructive operation. Hardware inventories remain local by default; sending them to an external model requires consent. A future RNN/LLM can summarize or rank recommendations only within validated compatibility rules and with a clear uncertainty label.


## Automated import and RNN-assisted candidate retrieval (2026-10-18)

- `tools/isa/import_riscv_opcodes.py` imports fixed-bit instruction encodings from an immutable upstream revision. The latest validated run imported 1,459 source-backed records from 141 files with zero file-fetch failures.
- `tools/isa/build_universal_catalog.py --input isa/sources/imports/riscv-opcodes.json` combines those records with the legacy database without asserting executable support. The latest generated catalog contains 1,613 forms across 15 architecture identifiers; all 1,613 currently remain `not-implemented` in execution status.
- `tools/isa/isa_candidate_router.py` and `tools/commands/command_candidate_router.py` use the existing bounded recurrent-state module for advisory ranking. This module is a deterministic research cell, **not a trained LLM**. It cannot infer authoritative semantics, create verified encodings, claim native support, or execute commands.
- Command import currently inventories 4,081 candidates: 15 backed by the existing native multicall allowlist and 4,066 deferred for provider discovery and tests. Unknown commands stay queued rather than falling back to arbitrary shell execution.
- The validated CI job persists generated source-backed catalogs and uploads the same run's artifact. Catalog, decode, execution, conformance, and userspace-ready are separate evidence levels.
